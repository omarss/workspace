# Saudi Salary Intelligence Model — Design v1

This document captures the end-to-end design that the v0 codebase implements, plus the
v0 iteration history. It is the on-disk source of truth for *why* the system looks the
way it does. When future sessions or contributors need the rationale for a decision,
read this first.

The chat that originally produced this design (with the 19-section answer) lives in
session transcripts; this file is the durable record.

---

## 1. Problem framing

**This is not a regressor on `salary`.** It is a *conditional distribution estimator
over compensation components* for a Saudi labor-market segment, with explicit
separation between *what the market pays* and *what is fair to pay*.

### Targets (predict each separately, then aggregate)

| Target | Symbol | Why separate |
|---|---|---|
| Monthly base salary (SAR, gross) | `base_monthly` | Most reliable, GOSI-reportable, the legal "wage" |
| Housing allowance (monthly) | `housing_monthly` | KSA convention: 25% of base or fixed; varies by sector |
| Transport allowance (monthly) | `transport_monthly` | Often 10% of base; capped in public sector |
| Other fixed allowances (monthly) | `other_fixed_monthly` | Phone, COLA, education, schooling, ticket amortization |
| Variable cash (annualized → monthly equivalent) | `variable_monthly_eq` | Sign-on, target bonus, commission, profit-share |
| Total cash compensation (monthly) | `tcc_monthly` | Derived: sum of above |
| Equity / LTI (annualized expected value) | `equity_annual_ev` | Only meaningful in tech, PIF-backed, listed cos |

### Why a distribution, not a point estimate

A 32-year-old Saudi backend engineer with 7 YOE in Riyadh at a PIF-backed scaleup can
earn anywhere from ~18k to ~45k SAR/month base depending on signaling, negotiation,
prior comp, scarcity of stack, and employer's salary band policy. Reporting `28,000 SAR`
is dishonest precision. We report **p10 / p25 / p50 / p75 / p90 with
coverage-calibrated intervals** and the *number of comparables*.

### Two parallel heads off the same model

1. **Descriptive head** — "what the market currently pays" (uses all features,
   including sensitive). For auditing, research, policy.
2. **Recommendation head** — "what should be paid" (sensitive features ablated). For
   employer-facing benchmarks.

These must never be conflated in the API contract.

## 2. Data sources

### Live in v0
- **World Bank WDI** — live REST API (`data/sources/worldbank.py`)
- **GASTAT / SAMA / HRSD** — bundled aggregates tagged `is_estimate=True`
- **Monthly macro time series** — bundled monthly CPI/policy/Brent joined per-row
  via `merge_asof` on `observed_at` (`data/sources/macro_series.py`)

### Stubbed for future integration (loader scaffolds with `NotImplementedError` until access)
- GOSI microdata, MUDAD aggregates, Mercer TRS, Lightcast postings, employee survey

### Open sources catalogued in the research pass (not yet wired)
- KAPSARC OpenDataSoft API (free, authoritative KSA labor)
- data.gov.sa CKAN API (11k+ datasets)
- ILOSTAT SDMX (international authoritative on KSA labor)
- GCC-Stat, MOF budget PDFs, Vision 2030 VRP annual reports
- Tadawul issuer disclosures
- Free salary survey PDFs: Hays, Cooper Fitch, Robert Walters, GulfTalent
- Leading-indicator feeds: PIF News RSS, NEOM/RSG/ROSHN careers, SPA economy RSS

### Synthetic anchored observations
Individual-level rows are synthesized **anchored to the public aggregates above**.
Every row carries `source = "synthetic_anchored"` and `confidence = 0.6` so the
training pipeline knows to weight real survey rows higher when they arrive.

## 3. Data model

PostgreSQL 16 + `pgvector` (embeddings) + `timescaledb` (hypertables for
`econ_indicators`, `job_postings`) is the target production datastore. The full DDL
draft is in the original §3 of the design (preserved in session history); a high-level
summary:

- `salary_observations_raw` + `salary_observations` (canonical) + `data_quality_flags`
- Reference: `job_families`, `seniority_levels`, `job_titles_normalized`, `skills`,
  `sectors`, `companies`, `regions`
- Macro: `econ_indicators` (timescale hypertable), `job_postings`
- Output: `predictions`, `explanations`, `model_versions`

Sensitive columns (`is_saudi`, `gender`, `age_bucket`) live in the same table but are
gated via column-level RLS / a `pii` role; the recommendation head is trained on a
view that excludes them. In v0 we use Parquet snapshots instead of Postgres, but the
column shapes match so the migration is straightforward.

## 4. Compensation normalization

The canonical comp tuple (all monthly, SAR, gross):

```
CanonicalComp = (base, housing, transport, other_fixed, variable_eq, equity_ev_annual)
```

Implemented in `data/normalize.py`. Rules:

1. **Period.** Annual / 12; hourly requires `weekly_hours`; daily × 22.
2. **Currency.** Convert to SAR via SAMA monthly average FX; record `fx_to_sar`.
3. **Gross vs net.** KSA personal income tax = 0; GOSI ~9.75% for Saudis. Gross-up
   net amounts only for Saudis; flag with `gross_estimated_from_net`.
4. **Housing.** Default 25% of base when known; conservative null otherwise (never
   silently impute zero — biases TCC down).
5. **Transport.** 10% of base when known; conservative null otherwise.
6. **Variable.** Cap at 100% of base (300% for sales).
7. **Equity.** Annual expected value; 0 for private/startups.
8. **Contractor.** Multiply base by 0.78 to approximate employee-equivalent;
   tag `contractor_to_employee_equiv`.

**TCC = base + housing + transport + other_fixed + variable_eq + equity_annual_ev/12.**

## 5. Title, level, skill normalization

Implemented in `data/taxonomy.py`. Two stages:

### Stage A — Rules + alias dictionary (fast, deterministic)
- Arabic NFKC normalization + dialect map
- Strip seniority tokens via regex
- Alias dictionary lookup (curated ~5k entries for KSA)

### Stage B — Embedding fallback (lazy-loaded)
- `intfloat/multilingual-e5-small` for Arabic + English
- Cosine nearest-neighbor against canonical family embeddings
- Accept if cosine ≥ 0.82; else escalate to manual curation queue

### Level inference
- Token map (`senior` / `manager` / `principal` / ...) → Level enum
- Fallback: yoe-bucket → Level

## 6. Feature engineering

Implemented in `features/build.py`. Groups:

- **Individual/job**: family_id, level_id, yoe, yoe², education_rank
- **Company**: ownership, size_bucket, is_pif_or_mnc
- **Region**: region_id, is_metro, region_base_multiplier
- **Sector**: sector_id, sector_base_median, log_sigma_sector
- **Macro (time-varying via `merge_asof`)**: cpi_yoy + lags 1/3/6/12,
  policy_rate + lags 1/3/6/12, brent_usd, brent_yoy, brent_3m_avg, sar_to_usd
- **Time**: month_sin/cos, year_ord, vision_phase
- **Sensitive (descriptive head only)**: gender_code, is_saudi, age_bucket_ord

### Leakage guards
- Time-based train/val/test split (`split_indices`), never random
- All rolling/lag joins use `ts ≤ observed_at - lag`
- `merge_asof(direction="backward")` for macro joins

### Two views
- `feature_columns_full()` — descriptive head (sensitive included)
- `feature_columns_blind()` — recommendation head (sensitive excluded)

## 7. Modeling approach (staged)

Per `models/`:

| Stage | Model | Purpose | Used in v0 |
|---|---|---|---|
| 1 | Ridge on log(target) | Sanity floor, drift baseline | yes |
| 2 | LightGBM single-point L1 | Robust point estimate | yes |
| 3 | LightGBM quantile bundle (5 q's) | Core distribution head | yes |
| 4 | Conformal calibration (asymmetric split CP) | Coverage-calibrated intervals | yes |
| 5 | Retrieval (kNN over standardized features) | Sparse-cell fallback, transparency | yes |
| 6 | Hierarchical Bayesian shrinkage (NumPyro / empirical) | v2; in v0 it's a diagnostic only |
| 7 | Time-series forecasting (statsforecast) | v3; not yet built |
| 8 | Ensemble / stacker | v3; not yet built |

## 8. Recommended production architecture

### v0 (shipped)
- LightGBM quantile (5 boosters) + asymmetric split conformal + retrieval blend
  gated to sparse cells (`n_cell < 5`) only
- Fairness recommendation head trained on blinded features + reweighted samples
- Bayes shrinkage retained as a diagnostic on the bundle, not blended into the
  headline prediction (proven harmful on synthetic data; revisit on real data)
- SHAP TreeExplainer on the p50 booster, serialized into the bundle
- Drift monitor (PSI per feature) callable via `make drift`

### v1 (next)
- Replace bundled GASTAT/SAMA estimates with KAPSARC + data.gov.sa + ILOSTAT live
  fetchers
- Wire MOF budget cycle features
- Stratified conformal per (family × region)

### v2 (later)
- Real microdata integration (GOSI / Mercer / MUDAD)
- Hierarchical Bayesian shrinkage **re-enabled** once parametric anchors are weaker
- Continual fine-tuning from incoming employee/employer surveys via warm-started
  LightGBM (see CLAUDE.md "fine-tuned with real survey data" section)

### v3 (research)
- Time-series segment-wage forecasts
- FT-Transformer / SAINT bake-off against the GBM if we cross 100k real rows
- Sentence-transformer embeddings of job descriptions when Lightcast lands

### Do NOT build initially
- Deep neural networks / transformers for the structured-feature task (literature
  says GBM wins below ~500k rows; we have 20k synthetic)
- LLM-based salary advisor in the prediction loop
- Causal models for "what raise should I ask for"
- Real-time / streaming

## 9. Prediction output

See `api/schemas.py::PredictResponse`. Every response carries:

- `descriptive.base` quantile block (p10/p25/p50/p75/p90) + per-quantile `labels`
  (human-readable: "top 10% — only 10% earns more")
- `recommendation` (when `head="recommendation"`)
- `confidence` (score + drivers)
- `comparables` (n + parametric weight)
- `explanation` (top-5 SHAP factors)
- `warnings` (low_n_segment, etc.)
- `fairness` (flag + sensitive features used)
- `data_provenance` (trained_on_real_data, training_mix, snapshot_hash)

---

## 10. Comparable / retrieval system

`models/retrieval.py`. Composite similarity in standardized feature space with
exact-region filter; fall back to unfiltered when in-region neighbors < 20. Gated
blend with parametric only when `n_cell < 5` (proved over-blending hurts on
synthetic data).

---

## 11. Bias, fairness, governance

- Descriptive head sees sensitive; recommendation head doesn't
- Counterfactual fairness audit per run: flip gender, flip is_saudi, measure p50 delta
- v0 result on synthetic: recommendation head |gap| = **0.00%** on both axes
  (literally cannot condition on them); descriptive shows the seeded ~7% gender gap
- Promotion gate: `fairness_median_abs_gap_max_pct = 0.02` for the recommendation
  head; never weakened without explicit user approval

---

## 12. Evaluation

`training/evaluate.py`:
- MAE, MAPE, sMAPE, RMSE for p50
- Pinball loss per quantile
- Interval coverage + width (target 80% / 90%)
- Slice scorecard per (family × region × level × ownership × gender × is_saudi)
- Counterfactual fairness audit

---

## 13. Monitoring and recalibration

`monitoring/drift.py`:
- PSI per feature, ref vs current
- Thresholds: 0.10 warn, 0.25 alert
- CLI: `make drift CURRENT=path/to/observations.parquet`
- Markdown + JSON report writers

Recalibration cadence (documented, not yet automated):
- Monthly retrain on rolling 24-month window
- Triggered retrain on MAPE +25%, PSI > 0.3 on top features, or coverage breach

## 14. System architecture

```
Sources (live + bundled + scaffolded)
    ↓
data/build.py — versioned Parquet snapshot + manifest
    ↓
features/build.py — leakage-safe feature pipeline + macro merge_asof
    ↓
training/iterate.py — full ladder (Ridge → LGBM L1 → quantile → conformal →
    ablation → Optuna → retrieval → fairness → v2_final) + MLflow + bundle save
    ↓
artifacts/model_bundle_latest.joblib
    ↓
api/app.py — FastAPI; loads bundle once at startup
```

Containerized via `Dockerfile` (multi-stage uv builder + non-root runtime), CI via
`.github/workflows/ci.yml` (gated on `ready` label).

## 16. Data quality and fraud prevention

Per-record `confidence` score (0..1) = weighted product of:
- Source-trust prior (0.30 weight)
- Schema completeness (0.10)
- Cross-source consistency (0.15)
- Plausibility (0.15)
- Recency (0.10)
- Internal consistency (0.10)
- Non-duplicate (0.10)

Specific detectors planned:
- MinHash LSH for duplicates
- Impossible values (below min wage for Saudis, above 500k SAR)
- Currency mistakes (auto-rescale candidate)
- Monthly/annual confusion
- Inflated self-reports (IsolationForest on residuals)
- Outdated (recency decay)

## 17. v0 iteration journey (the actual receipts)

Five iteration cycles + the v0 production bundle (`reports/runs/v0/`):

| iter | hypothesis | final mae | conclusion |
|---|---|---:|---|
| v0-iter   | first full ladder run | 7,774 | huber single-point misα; retrieval + Bayes blends too aggressive |
| v0-iter-2 | regression_l1; batched retrieval; lighter Bayes | 7,252 | step-1 -44% mae; retrieval 14× faster |
| v0-iter-3 | hard-gate retrieval & shrinkage to sparse cells | 7,720 | retrieval gating helped; shrinkage *worse* |
| v0-iter-4 | shrinkage only at n≤1 | 7,100 | better but global mean for unseen cells is worse than parametric |
| v0-iter-5 | Bayes off prediction path; diagnostic only | **6,360** | converged |
| **v0**    | + serialized category codes | **6,360** | reproducible end-to-end + API works |

Each iteration has a `notes.md` in `reports/runs/v0-iter*/` explaining what was tried.

## 19. Where this can fail (honest)

1. **No GOSI/MUDAD microdata.** Without it, selection bias is severe; the model
   over-represents white-collar Riyadh tech and badly under-represents retail,
   hospitality, construction, blue-collar expat. Plan: pursue legal track in
   parallel.
2. **Title normalization noise compounds.** Budget human curation time.
3. **PDPL + GOSI legal review** can add months.
4. **Vision 2030 cycle effects** distort historical patterns.
5. **Self-reported user data is gameable** the moment the product is useful.

### What you must have for it to work
- ≥ 50k normalized observations across ≥ 200 cells with ≥ 30 each
- Reliable monthly macro feed
- Title/level/skill taxonomy committed in writing
- One human curator at ≥ 0.5 FTE

### What cannot be predicted reliably
- Individual outliers (negotiated outperformer, founder discount/premium)
- Sign-on bonuses / one-off equity grants
- Family businesses < 50 employees
- Sub-12-month forecasts of mega-project comp shifts
- Net take-home for non-Saudi expats with complex packages
- Sub-segments with N < 200

### Fastest path to a useful, honest version

Weeks 1-12 plan, already executed for v0; v1 priorities now:

1. Real KAPSARC + data.gov.sa + ILOSTAT fetchers (replace bundled anchors)
2. Tighten provenance plumbing (already started; `data_provenance` in API)
3. Pursue GOSI legal track in parallel
4. Once survey data lands, fine-tune via LightGBM `init_model=` warm-start
