Operator Walkthrough

Five concrete tasks. Each is one CLI call, one curl, and the expected response. About ten minutes end-to-end.

Who you are

You are the platform operator. You stand up Deployments, attach custom domains, freeze a tenant's encryption keys when an incident lands on the rota, and read the audit log when compliance asks. Your CLI is saasctl; your auth token comes from the operators realm in Keycloak (see ADR 019).

Prerequisites

  • Local stack up: saasctl init finished, or you ran make compose-up and the migrations yourself.
  • Operator bearer token cached at ~/.saas/credentials.json (the wizard wrote it for you on --operator-token-file; otherwise the CLI falls back to the mock headers in local-dev).
  • Familiarity with the first-class recipes for deeper detail.

Step 1 — Provision a Deployment

Recipe: provision-deployment.

$ saasctl deployment create \
    --project default \
    --environment dev \
    --image v0.3.1
Deployment created: dep_01HXAAAAAAAAAAAAAAAAAA
Primary vhost:      https://dev.default.saas.omarss.net
Bootstrap API key:  api_01HXBBBBBBBBBBBBBBBBBB
Bootstrap secret:   sk_live_…   # COPY NOW — shown ONCE
One-shot secret. The bootstrap secret is shown once. Pipe it to your secret manager immediately. If you lose it, rotate the API key — the original secret cannot be recovered (ADR 008).

Step 2 — Inspect the §6.2 step ledger

Provisioning runs nine adapters in sequence (nginx, k3s, Postgres, OpenBao, …). The ledger shows which step is at which state — useful when a Deployment is stuck in provisioning. 

$ saasctl deployment ledger dep_01HXAA…
{
  "data": [
    {"step": "nginx_vhost",     "state": "applied"},
    {"step": "k3s_namespace",   "state": "applied"},
    {"step": "postgres_db",     "state": "applied"},
    {"step": "openbao_transit", "state": "applied"}
    …
  ]
}

Step 3 — Attach a custom domain (BYOD)

Recipe: attach-custom-domain.

  1. Attach. 
    $ saasctl domain attach dep_01HXAA… --domain app.acme.test
{
  "data": {
    "id": "dom_01HX…",
    "state": "pending_verification",
    "txt_record": { "name": "_saas-verify.app.acme.test", "value": "saas-verify=abc…" }
  }
}
  2. Publish the TXT record on the customer's authoritative DNS. Wait for propagation (dig +short TXT _saas-verify.app.acme.test should return the value).
  3. Verify. 
    $ saasctl domain verify dep_01HXAA… --domain-id dom_01HX…
{"data":{"state":"verified","cert_issued_at":"…"}}
Cert vs. apply-nginx. The control plane re-renders the per-Deployment vhost and runs nginx -s reload — it does NOT call homelab's make apply-nginx, which would clobber certbot's 443 blocks (workspace gotcha #1).

Step 4 — Freeze keys (incident response)

When a tenant suspects an in-progress compromise you can freeze their per-Deployment OpenBao transit key without taking the rest of the Deployment down (ADR 016, §18.7). 

$ saasctl deployment freeze-keys dep_01HXAA… \
    --reason "PD-1234 — investigating suspicious data export"
{"data":{"frozen_at":"…","by":"op_01HX…"}}

After freeze, reads continue (existing data plane sessions cache the DEK), but no new envelope-encrypted writes succeed. Unfreeze via the same endpoint with --unfreeze once the incident is closed.

Step 5 — Read the audit chain

Recipe: view-audit-events.

$ saasctl audit list \
    --tenant tenant_01HX… \
    --since  2026-05-20T00:00:00Z \
    --limit  20
{
  "data": [
    {
      "id":     "audit_01HX…",
      "actor":  "user_01HX…",
      "action": "tenant.create",
      "at":     "2026-05-26T10:11:12Z",
      "prev":   "blake3:…",
      "self":   "blake3:…"
    }
  ],
  "next_cursor": "v1:…"
}

Integrity verification is a separate control-plane endpoint: 

$ curl -X POST \
    "https://control.saas.omarss.net/control/v1/deployments/$DEP_ID/audit-integrity" \
    -H "Authorization: Bearer $OPERATOR_TOKEN" \
    -H "Idempotency-Key: idem_$(uuidgen)"
