# ADR 006 — OpenBao Shamir 5-of-3 unseal for MVP; cloud KMS in roadmap

## Status

Accepted — 2026-05-24.

## Context

AGENTS.md §18.7 requires OpenBao envelope encryption from MVP. OpenBao does
not ship a file-based or environment-variable auto-unseal seal (the `static`
seal exists but is documented dev-only and produces unsealed-on-boot
behaviour that's unacceptable for any storage holding real data).

The cloud KMS auto-unseal stanzas — `awskms`, `gcpckms`, `azurekeyvault`,
`alicloudkms`, `ocikms`, `transit` (Vault-to-Vault) — all require an external
cloud account or a second OpenBao cluster the homelab does not currently
operate. The homelab MVP runs on a single host with no external KMS
relationship.

That leaves two real options for MVP:

1. **Shamir 5-of-3 with scripted unseal at boot**, share-1 stored on a
   tmpfs path inside the container, shares 2-5 held offline by the operator.
   The first boot also captures the root token; the bootstrap script revokes
   it after enabling the auth methods + engines + audit device.
2. **Operator-prompted unseal at every container start**, with no shares on
   disk. Safer cryptographically but breaks `docker compose up -d` because
   the bao container would never become healthy without manual input.

Decision: option (1) for MVP, with a clear migration path to cloud KMS
auto-unseal documented in this ADR.

## Decision

MVP (today):

- Initialise OpenBao with `bao operator init -key-shares=5 -key-threshold=3`
  on first container boot. The bootstrap script in
  `deploy/openbao/init/entrypoint.sh` does this.
- Persist the init payload (5 shares + root token) at
  `/openbao/secrets/init.json` (mode 0400, on a named Docker volume so the
  share survives container restarts). The container reads the first three
  shares to unseal on subsequent boots.
- The named volume is **dev-only**. In production the share file does not
  exist on disk at all — cloud KMS auto-unseal replaces it. The trade-off
  here is convenience (auto-unseal across restarts) for an extra surface
  area (anyone with write access to the openbao-secrets volume can extract
  shares). Host-level disk encryption is the compensating control on the
  homelab.
- Shares 2-5 are exfiltrated by the operator after the first init and kept
  offline (paper, hardware token, or a 1Password vault entry — operator's
  call, documented in the runbook).
- Root token is generated by init; subsequent operations go through AppRole
  (control-plane host) or Kubernetes auth (data-plane pods). The bootstrap
  script revokes the root token after enabling engines + auth methods +
  audit device.
- Audit device enabled at `/openbao/logs/audit.log`; rotated weekly via host
  systemd timer (deferred to a follow-up phase).

Production (when the platform leaves the homelab):

- Migrate to cloud KMS auto-unseal via the appropriate `seal` stanza in
  `openbao.hcl`.
- Migration is a one-time `bao operator migrate` followed by a reseal.
  Steps will be documented in `docs/runbooks/openbao-cloud-kms.md`.
- The MVP bootstrap script is then retired; the production overlay replaces
  the seal stanza and does not generate or store Shamir shares.

## Consequences

Positive:

- Works end-to-end on the homelab today with no external dependencies.
- Aligns with the documented threat model (single-host, single-operator).
- Reproducible: re-running the bootstrap is a no-op on a healthy container.

Negative:

- The tmpfs share file is a known single-host risk. An attacker with root
  on the host can extract share-1 from memory. Mitigation: the host runs
  behind the workspace's Saudi-only ipset geofence + SSH key-only auth.
  Production target is cloud KMS auto-unseal.
- A cold-boot loses the tmpfs share file. If the openbao-data volume has
  pre-existing data and the share file is gone, the bootstrap script refuses
  to re-init (would lose all data) — the operator must paste 3 shares
  manually via `bao operator unseal`. Documented behaviour, not a bug.
- Re-initialising loses every encrypted DEK. Backups (`bao operator raft
  snapshot save`) are out of scope for Phase 4 and are tracked under the
  production-readiness checklist.

## Alternatives considered

- **`static` seal**: refused. Dev-only per upstream docs; unsealed on every
  boot means anyone with read access to the storage volume has every secret
  in plaintext. Unacceptable.
- **Cloud KMS auto-unseal at MVP**: defers MVP delivery until a cloud KMS
  account exists. Mismatched with the homelab strategy.
- **PGP-encrypted Shamir shares + operator prompt at every boot**: safer
  but blocks `docker compose up -d`. We may revisit when the platform
  serves real customer data.

## Implementation pointers

- Bootstrap script: `deploy/openbao/init/entrypoint.sh`
- OpenBao server config: `deploy/openbao/config/openbao.hcl`
- Per-Deployment policy template: `deploy/openbao/policies/deployment.hcl.tmpl`
- Make targets: `openbao-init`, `openbao-status`, `openbao-rotate`,
  `openbao-policies`, `openbao-approle-creds`
- Code that consumes the bao client: `internal/platform/crypto/envelope/`
